# WI-003 (payment-service core and getOrder) acceptance criteria → code and tests

The service shell, bearer auth, `GET /api/v1/orders/{orderId}` (projection cache, 404/502 mapping via the
WI-002 `OrderService` adapter) and the pay page's order section were built in WI-1/WI-2/WI-002. WI-003
moves the "what does the order section show" decision into DOM-free `orderView` (`web/public/js/payment.js`,
used by `pay-page.js` `loadOrder`), formats amounts by the currency's own minor-unit exponent without float
arithmetic, and requires a summary.

End-to-end: `tests/e2e/pay_flow.test.mjs` suite "WI-003 acceptance" (run by `tests/test_e2e_payment_flow.py`,
live server, auth on, orders `orderView` = 349900 INR and `orderViewJpy` = 1500 JPY).

| AC | Behaviour | Code | Tests |
|---|---|---|---|
| 1 | Missing order id → error, not a blank field | `validateOrder` (id must be a UUID; summary required) → `orderView` `ok: false` → `showOrderUnavailable` | unit "WI-003 … AC1", e2e "AC1, AC2" |
| 2 | No currency → no amount shown | `formatAmount` returns null without a valid ISO code; `validateOrder` → `orderView` error | unit "WI-003 … AC2", e2e "AC1, AC2" |
| 3 | getOrder fails → error, no blank/stale amount | `orderView({error})` ignores any previous order; `showOrderUnavailable` clears id/summary/amount; API 502 caches nothing, 404 for unknown/foreign order, 401 without token | unit "WI-003 … AC3", e2e "AC3"; `test_order_service_failure_is_502`, `test_order_service_failure_caches_nothing_and_later_succeeds`, `test_get_unknown_order_is_404`, `test_get_order_requires_bearer_token` |
| 4 | Exact backend amount rendered | `formatAmount` → `minorToDecimal(amount, Intl maximumFractionDigits)` (JPY 0, INR 2, KWD 3), exact decimal string to `Intl.NumberFormat` | unit "WI-003 … AC4", "minorToDecimal …", e2e "AC4" (JPY); `test_get_order` |
