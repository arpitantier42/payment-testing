# WI-004 (createPayment: idempotent initiation and gateway handoff) acceptance criteria → code and tests

`POST /api/v1/payments` and the Pay Now controller were first built in WI-1/WI-2. WI-004 completes the
operation's declared steps and error paths:

- **Step 1, revalidate with order-service (REQ-006):** a new attempt (not a replay) re-fetches the order from
  order-service before anything is stored or sent to the gateway. order-service down → 502
  `order_service_unavailable`; order gone → 404; amount/currency differ from the cached projection → 409
  `order_changed` (the projection is never overwritten, HLD RSK-002). Nothing is stored or charged.
- **409 also for a different amount:** a replayed `Idempotency-Key` whose request carries an amount/currency other
  than the original payment's → 409 `idempotency_conflict` (contract: "different order or amount").
- **502 for any gateway failure:** not only `GatewayError` but any exception from the adapter (timeout, connection
  error) marks the attempt `failed` and answers 502, so no payment is left `initiated` (which would block the
  key rotation and therefore any retry).
- **Concurrency (HLD NFR-003):** API-level test firing two simultaneous POSTs with one key.

Code: `src/payment_service/api/routes.py` `create_payment`; frontend `createPayNowController` in
`web/public/js/payment.js`, `pay-page.js` reads the checked radio at submit time.

End-to-end: `tests/e2e/pay_flow.test.mjs` suite "WI-004 acceptance" (orders `wi004Method`, `wi004Errors`,
`wi004Conflict`, `wi004Double`), DB checks in `tests/test_e2e_payment_flow.py`.
